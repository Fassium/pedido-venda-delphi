2. Ambiente e banco

Por que o projeto é Win64?

  • O executável só carrega uma DLL da mesma arquitetura: um exe 64 bits não carrega o fbclient.dll de 32. Instalei o Firebird 5 x64 e mando o fbclient.dll x64 no bin.
  • 64 bits é o padrão do Windows hoje e tira o limite de memória de um processo 32 bits.
  • O servidor Firebird pode ser 32 ou 64 bits: o sistema fala com ele por TCP (porta 3050). Só o cliente (fbclient.dll) precisa ser x64 como o exe.
  • O fbclient.dll 5.0 depende do runtime do Visual C++, então as três DLLs dele (msvcp140, vcruntime140, vcruntime140_1) vão junto no bin. Assim roda mesmo sem o VC++ Redistributable instalado.

Por que Firebird 3.0 ou mais novo?

O db.sql usa GENERATED BY DEFAULT AS IDENTITY no PEDIDO_ITEM.ID, que só existe a partir do Firebird 3.0.

Como o número do pedido é gerado?

Com uma SEQUENCE (NEXT VALUE FOR SEQ_PEDIDO_NUMERO) no próprio INSERT, e o número volta pelo RETURNING. Não precisa de trigger nem de um SELECT a mais. A sequence não volta atrás no rollback, então o número é crescente, mas pode pular.

Por que os índices das FKs têm nome com USING INDEX?

No Firebird a FK já cria um índice. Se eu criasse outro CREATE INDEX na mesma coluna, ficaria duplicado. Com USING INDEX o índice da FK ganha um nome padronizado (IDX_...) e o enunciado é atendido sem duplicar.

Por que não usou ON DELETE CASCADE?

Para a exclusão ficar explícita no código: o cancelamento apaga os itens e depois o pedido, na mesma transação. Com cascade, alguém que apagasse um pedido direto no banco levaria os itens junto sem perceber.

Como o sistema sabe onde está o banco?

Pelo bin\config.ini, lido ao abrir o sistema (Infra.Configuracao). A conexão é criada em código (Infra.Conexao), sem conexão em design-time. O config.ini guarda senha, então não vai para o Git; o repositório tem o config.ini.example para copiar.

Por que Currency e não Double?

Currency é ponto fixo com 4 casas: soma e multiplicação de dinheiro dão o valor exato. Double é ponto flutuante e pode gerar diferenças de centavos. No banco, NUMERIC(15,2).

3. Arquitetura

Por que separar em View, Controller, Service e Repository?

Cada camada tem uma responsabilidade só:

CamadaFazExemplo
ViewMostra e lê dados da tela, sem SQL e sem regraView.PedidoVenda
ControllerMonta as peças (cria os repositórios e o Service) e é a porta de entrada da telaController.Pedido
ServiceRegra de negócio e transaçãoServico.Pedido
RepositorySó o SQL de uma tabela ou agregadoRepositorio.Pedido
ModelAs entidades e a regra do totalTPedido, TPedidoItem
InfraConfiguração e conexãoInfra.Conexao

O ganho é manutenção: trocar a tela não mexe no SQL, trocar o banco não mexe na tela, e a regra fica num lugar só, onde dá para testar.

Por que os repositórios têm interface?

O Service recebe IRepositorioPedido, e não a classe concreta (inversão de dependência, o "D" do SOLID). Assim dá para trocar o repositório, por exemplo por um falso em teste, sem mudar o Service. A interface também gerencia a memória por contagem de referência.

Por que a transação fica no Service e não no Repository?

Porque só o Service sabe que gravar um pedido envolve duas tabelas (cabeçalho e itens). Se cada repositório abrisse a sua transação, um erro no item deixaria o cabeçalho gravado pela metade. No Service: StartTransaction, grava tudo, Commit; em qualquer erro, Rollback e a mensagem aparece sem perder o que foi digitado.

Por que o total fica no Model?

TPedido.ValorTotal sempre soma os itens na hora em que é lido; não é um valor guardado. Então incluir, alterar ou excluir um item nunca deixa o total errado, e a correção 4.2 (total ao excluir item) sai certa por construção. A tela só exibe.

Por que o grid dos itens é um TStringGrid e a lista é um TDBGrid?

Os itens vivem no objeto TPedido até o Gravar; o grid só desenha a lista (linha N = item N-1). A lista de pedidos vem de um SELECT com JOIN, então ela é um TFDMemTable ligado a um TDBGrid.

Como funciona a edição de um pedido já gravado?

UPDATE no cabeçalho, apaga os itens e grava de novo, tudo na mesma transação. É mais simples e seguro que comparar item a item; o custo é os itens ganharem IDs novos. Se o pedido sumiu do banco (RowsAffected = 0), a gravação é desfeita.

Por que as queries são parametrizadas?

Para evitar SQL injection e deixar o banco reaproveitar o plano da consulta. Até o filtro da lista, que monta o WHERE conforme o que foi digitado, passa o valor por parâmetro.

4. Testes unitários (DUnitX)

Qual a função da classe de teste TTestePedido?

É a fixture ([TestFixture]) que agrupa os testes da regra do total do pedido. Antes de cada teste, o [Setup] cria um TPedido novo; depois de cada um, o [TearDown] libera. Assim um teste nunca interfere no outro. Os 5 testes cobrem o que a tela faz com o total: pedido vazio, total do item, soma dos itens, atualizar item e excluir item.

Ela testa só o Model, sem banco e sem tela. Por isso roda em milissegundos e em qualquer máquina.

Que erro esses testes pegariam?

Qualquer mudança que quebre o total: alguém passar a guardar o total num campo e esquecer de atualizar ao excluir; trocar Currency por Double; ou mudar a lista para TList e o Delete deixar de liberar o item.

Por que Assert.AreEqual<Currency>?

O genérico força a comparação como Currency, que é exata. Sem ele, o compilador pode escolher a versão com Extended, que é ponto flutuante. O valor esperado vem primeiro, para a mensagem de falha sair certa.

Por que o projeto de testes é separado?

Para o executável que vai ao cliente não levar código de teste. O projeto de testes usa só as units do Model (..\src\pedidos\Model.*.pas) e gera o exe em tests\bin, fora do Git.

Qual o resultado de colocar esses testes num pipeline de CI/CD?

O exe de testes já foi feito para isso: termina com código de saída diferente de zero quando algum teste falha, e gera o dunitx-results.xml no formato NUnit. Num pipeline (Jenkins, GitHub Actions ou Azure DevOps, com um agente Windows que tenha o Delphi instalado):

  1. a cada push, o pipeline compila o projeto de testes com MSBuild;
  2. roda o exe; se um teste falhar, o código de saída quebra o build;
  3. publica o XML como relatório de testes.
call "C:\Program Files (x86)\Embarcadero\Studio\37.0\bin\rsvars.bat"
msbuild tests\PedidoVendaTestes.dproj /t:Build /p:Config=Release /p:Platform=Win64
tests\bin\PedidoVendaTestes.exe

O resultado: um erro na regra do total é barrado antes de chegar à branch principal e ao cliente; o time ganha segurança para refatorar e um relatório do que foi testado em cada versão. O .dpr gerado pelo DUnitX tem um {$IFNDEF CI} para nunca pausar esperando o Enter quando compilado para o pipeline.

5. Processo

Por que tantos commits pequenos?

Cada commit é uma mudança que dá para entender e desfazer sozinha. O histórico conta a evolução, por exemplo a Observação (4.1) entrou num commit próprio, e a trilha liga cada passo aos seus commits.

Encontrou algum problema difícil?

Sim: o erro [FB]-338 ao gravar. O tipo de um parâmetro de valor mudava depois do Prepare. A solução foi declarar os parâmetros de valor como ftCurrency antes de preparar. O rollback no erro provou que o cabeçalho não ficava gravado pela metade.

Como usou IA no projeto?

Fiz em pair programming com o Claude Code. Eu conduzi as decisões, testei cada passo no Delphi, encontrei e reportei os erros e fiz todos os commits. A IA propôs a estrutura em camadas, revisou o código, explicou o porquê de cada escolha e escreveu parte do código a pedido. Os testes DUnitX eu digitei, guiado passo a passo, porque era meu primeiro contato com o framework.
