Do problema do usuário até a produção

O caminho de uma correção numa empresa de software, e onde entram os testes automatizados.

O fluxo

Cada etapa

#EtapaO que acontece
1UsuárioPercebe um problema, por exemplo o total do pedido errado ao excluir um item.
2SuporteAtende, reproduz o problema e abre o chamado com os passos.
3ProdutoAvalia o impacto no negócio e decide a prioridade.
4DocumentaçãoDescreve o comportamento esperado (história, regra, critério de aceite).
5DevCorrige o código e escreve um teste automatizado que prova a correção.
6CI/CDA cada envio de código, compila e roda todos os testes automatizados. Se um falhar, a versão para aqui.
7QualidadeTesta a versão como o usuário usaria: fluxos, telas e casos que a automação não cobre.
8ProduçãoA versão é liberada e o usuário recebe a correção.

O que o CI/CD faz neste projeto

  1. Compila o projeto de testes com MSBuild.
  2. Roda o PedidoVendaTestes.exe, que executa os 5 testes do total do pedido.
  3. Se algum teste falha, o exe termina com código de erro e o pipeline para a versão.
  4. Publica o dunitx-results.xml como relatório dos testes.

Ferramentas comuns para isso: Jenkins, GitHub Actions, Azure DevOps ou GitLab CI, com um agente Windows que tenha o Delphi instalado.

Quanto mais tarde o erro aparece, mais caro ele fica

As barras mostram a ideia, não uma medida exata: o mesmo erro custa pouco quando um teste o pega no dev e muito quando chega ao cliente.

Por que os testes automatizados são importantes

Pegam o erro cedoUm erro barrado no CI/CD volta para o dev em minutos, antes de chegar à qualidade e ao cliente.
Evitam regressãoUma correção nova não pode quebrar o que já funcionava. Os testes antigos continuam rodando a cada versão.
Rodam sempre igualO teste não esquece um passo e não se cansa. Os 5 testes deste projeto rodam em milissegundos.
Dão segurança para mudarDá para refatorar e melhorar o código sabendo que, se algo quebrar, o teste avisa.
Liberam a qualidadeO que é repetitivo fica com a máquina; a equipe de qualidade testa o que precisa de olhar humano.
Documentam a regraO nome do teste diz o comportamento esperado, por exemplo PedidoDeveRecalcularAoExcluirItem.

Exemplo com este projeto

Imagine que alguém muda o TPedido para guardar o total num campo, para "ganhar desempenho", e esquece de atualizar esse campo ao excluir um item.

  1. No dev, o código compila e a tela parece funcionar.
  2. No CI/CD, o teste PedidoDeveRecalcularAoExcluirItem falha: esperava 12,75 e recebeu 33,75.
  3. O pipeline para a versão e avisa o dev, que corrige em minutos.
  4. O erro nunca chega à qualidade nem ao cliente.

Sem o teste, esse mesmo erro só apareceria quando um usuário notasse o total errado num pedido gravado, e todo o fluxo começaria de novo na etapa 1.
